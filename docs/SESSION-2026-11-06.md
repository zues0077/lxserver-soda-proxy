# 会话纪要 · 2026-11-06（汽水受限曲整曲：从调研到接入）

> 这是「对话留档」，不是技术文档。技术细节看 `docs/HANDOVER.md`。
> 目的：新任务接手时知道**为什么这么做**、哪些结论被推翻过、哪些还没验。

---

## 一、这一轮要解决什么

用户诉求（原话大意）：

> 「帮我看看汽水为什么受限曲只能听 60 秒，能不能整曲。
> 我不想常开平板，是否可以像 PC 版那样用 Docker 来做这个事。」

拆成三个递进的问题：

1. 汽水为什么只有试听？**能不能整曲？**
2. 平板能不能换成 Docker？**换哪个宿主？**
3. 能不能**完全不要设备**？

---

## 二、每轮的关键结论（含被推翻的）

### 第 1 轮：找「按 track_id 单曲取链」的免签接口 → 找不到

- 最快的办法不是抓包，是**读 APK**：dex 里接口路径是 `..` 分隔的字符串池，
  按小写段提取得 **197 条候选**（`/luna/feed/song-tab`、`/luna/track/player`、`/luna/media_v2`…）。
- 逐条实测：`feed/song-tab` 免签可调但**只给元数据**（`id/vid/bit_rates/playable_range`），
  **没有 `video_model`**；`/luna/track/player` 恒 `1000006`（需 mssdk 签名）；
  `/luna/media_v2` 200 但 body 空；其余 404。
- **推翻了自己前一天的结论**（P-1144 说 feed 带密钥）：那是「真实 App + 登录态 + 签名」的
  请求结果，裸调复现不了。当时代码只改了文案，没有硬加 feed 通道（加了就是死代码）。

### 第 2 轮：搞清楚 App 的结构（三个「原来如此」）

- **播放走预取队列**：队列里有的歌直接读本地表，**不发请求** —— 这才是「切歌时抓不到请求」的真因，
  不是 hook 坏了。
- **取链结果在 `cached_playable`**，不是 `player_info`。`player_info` 只在队列预取时写。
- **抓包只看到 CONNECT** 是因为 **Cronet 不走系统代理**，流量压根没进代理 —— 不是证书问题，
  以后别再在 MITM 上耗时间。

### 第 3 轮：换思路 —— 让 App 自己取链，我们只读结果

这是整条路的转折点。三个已验证的事实：

1. **深链能指定歌曲**：`luna://luna.com/playing?track_id=<数字>`；
2. **hook JSON 解析能拿到 App 真正使用的 `video_model`**（`org.json.JSONObject` + `gson.fromJson`），
   里面每档都带 52 字符 `spade_a`；
3. **`spade_a` 能解整曲**：花鸦 151.706s / 6 档全 `encrypt=true`；
   `highest` 4935867B → 仓库现有解密 → 4883518B / **6536 帧 AAC 首元素 100% 合法**。

### 第 4 轮：闭环 —— 深链不行，必须「搜索 → 点歌」

- 深链能播，但**不进播放队列**（等 28s 队列条数不变），所以拿不到取链结果。
- **搜索歌名 → 点第一条 → 播放**：队列从 30 条涨到 37 条，目标 `track_id` 立刻出现 ✅
- 顺手解决了：中文输入（ADBKeyboard）、截图坐标 ×1.77 的坑。

压测 5/5：花鸦 1.0s（队列命中）、夜曲 1.2s、没那种命 ~70s（搜索兜底）、晴天 68s、稻香 59s；
端到端 3 首全部 100%（6536 / 12440 / 10224 帧）。

### 第 5 轮：用户问「不想常开平板，能不能用 Docker」→ x86 判死

- 先实测宿主能力：N100 那台**前置条件全满足**（内核 6.18 内置 `binder`、`binfmt_misc` 已挂载、
  fuse、KVM、Docker、磁盘都够），所以一度以为可行。
- 但汽水是 **arm64-only**（`secondaryCpuAbi=null`）。两个转译路线都试了：
  - NDK translation（Android 15）：`libsafe-mode-native-lib.so is for EM_AARCH64 instead of
    EM_X86_64`，崩在 `MainApplication.attachBaseContext`；
  - Houdini（Android 13）：`SIGSEGV / SEGV_MAPERR / zygote64`。
- **结论：x86 + ARM 转译对汽水是死的**，容器本身没问题，卡在 native 库。已清场。

### 第 6 轮：用户追问「这是要脱离平板吗、不需要平板就能用畅听？」

我的回答（**必须记住的口径**）：

> **能脱离平板，但不能脱离 Android 环境。**

- 整曲只能在手机客户端成立；签名逐请求生成 + 绑设备指纹 + 反调试；权益判定在客户端侧。
- 所以这条路不是「纯服务器破解」，是「把手机端的播放能力搬到服务端」。
- **也不是破解会员**：账号没有的权益，代理也拿不到。
- 真要「完全无设备」，只剩复刻 mssdk（成本极高、且实测 PC 端点签了也不给密钥）或放弃。

### 第 7 轮：用户问 RK3399 / RK3566 能不能跑

查 Docker Hub manifest：

```
redroid/redroid:15.0.0-latest → amd64(883MB) / arm64(821MB)
```

**原生 arm64，不需要转译** → x86 的死局在 ARM 上不存在。
「哪颗芯片行不行」的真正变量是**内核有没有 binderfs**（4.4 一定没有），不是芯片型号。

### 第 8 轮：设备不在线 → 把不依赖设备的活全干完

- lxserver 接入（`sodaProxy.ts` + `soda.ts`）+ 管理页配置入口 + 单测 6 例 + 诊断字段；
- 代理侧 `fast=1`、`vtype` 透传、`su` 自适应（redroid 里没有 su）、`.gitattributes` 锁 LF；
- ARM 部署件（体检脚本 + 起容器脚本 + Dockerfile + compose）；
- 文档 + 手册 4 条（P-1146/1147/1148/1150/1152/1154）。

### 第 9 轮

用户在外面，让把平板关机。关机前确认输入法已回豆包、代理 `:0`；
`adb shell "su -c 'reboot -p'"` → 48 秒后仍未上线 → 确认真关机。

## 三、用户的关键偏好（读一遍，别踩）

| 偏好 | 表现 |
|---|---|
| 要**诚实的能力边界** | 「这条能做什么、不能做什么」必须先说清，不允许用「理论上可行」糊过去 |
| 讨厌**无证据的乐观** | 所有结论都要带报错原文 / 实测数字 / manifest 这类硬证据 |
| 关注**投入产出** | 「x86 不可行」这种否定结论同样有价值，要写下来避免重复投入 |
| 先给**可选项 + 建议** | 「A/B/C 你选」的形式比「我替你决定了」更好 |
| 不许**擅自构建/发版** | 这次全程未构建、未发版，只推代码到 main |

## 四、这一轮真正学到的东西（可复用的方法论）

> 逐条的「现象 → 真因 → 正确做法」整理在 **[docs/PITFALLS.md](PITFALLS.md)**，
> 下面只讲方法论层面的东西。

1. **找接口读 APK 比抓包快十倍** —— dex 字符串池按 `..` 切分，一次拿全。
2. **App 的本地数据库是最好的「协议文档」** —— 它能告诉你 App 真正用了什么，
   比逆向签名便宜得多。但要先搞清「哪张表在什么时机写」，否则会像我一样在
   `player_info` 上白耗。
3. **否定结论要写进手册** —— x86 转译不可行这次记了两次实错的报错原文，
   下次谁再想试可以直接跳过。
4. **慢路径必须后台化** —— 60~90 秒的操作绝不能放在用户点歌的同步链路上，
   改成「后台预热 + 提示重试」体验差别巨大。
5. **`git reset --hard origin/main` 前先确认 fetch 成功** —— 本次 fetch 报 502 但 reset 照跑，
   把本地新提交（ARM 部署件）抹掉了，靠远端 Contents API 才还原。
