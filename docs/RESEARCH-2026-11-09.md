# 调研记录 2026-11-09：怎么把这套东西跑得更省

> 目的：在不牺牲「整曲 + spade_a」的前提下，把 206（RK3566 / 3.8GB / kernel 6.18 / cgroup v2）
> 上的占用压下来，并让 UI 自动化不再依赖硬编码坐标。
> 每条都标了「结论」和「来源」，没验证过的会写明「未验证」。

## 一、能不能不要安卓

### libresoda（Rust）+ libmssdk

- 仓库：`sodahub-org/libresoda`（AGPL-3.0，`guohuiyuan/music-lib` 的 Rust 移植），
  配套 `sodahub-org/libmssdk`（把官方客户端 `bdms.node` 包成 HTTP/stdio 签名服务）。
- **能力**：搜索 / 专辑 / 歌单 / 歌词 / 音质择优 / 加密流解密（spade + CENC）/ 扫码登录都在。
- **致命前提**（原文）：`/luna/pc/track_v2` 要求**逐请求**的应用级签名头 `x-helios` / `x-medusa`，
  由官方客户端的 `mssdk/metasecml.dll` 生成；不给签名 → `HTTP 200` + **空 body**，或只有 30~60 秒试听。
  而且同一对签名只对「URL + body 字节完全一致」的请求有效。
- 官方推荐架构就是**分离**：Windows/macOS 跑签名器，Linux 跑 libresoda（`QISHUI_SIGNER_URL`）。
- **结论**：这条路等价于「常开一台 Windows/Mac」。而实测 PC 端本来就没有手机端的畅听/整曲权益
  （我们自己的签名器早就验证过），所以即使跑通也拿不到我们要的东西。
  → **安卓 App 自己签名的路线不可替代**，至少目前是。

### 其它容器化安卓

- Waydroid：需要 Wayland/LXC，无头场景不适用。
- Cuttlefish / AVD：资源开销比 redroid 大一个量级。
- Anbox：已停更。
- **结论**：redroid 仍是唯一现实选择。

## 二、redroid 版本下限

- lmkd 的策略演进：Android 10 引入 PSI，**Android 11 起** lmkd 才基于 PSI + cgroup v2
  （`ro.lmk.use_psi=true` 默认；需要内核 `CONFIG_PSI=y`）。
- 实测 Android **8.1** 在这台机器上：lmkd 读 `/dev/memcg/memory.usage_in_bytes`（cgroup v1 路径）失败 →
  反复杀前台 App；dex2oat 也失败（`Failed to dexopt (code 512)`）→ 永远解释执行、冷启动 5 分钟。
  → 8.1 不可用（详见手册 P-1362）。
- **结论**：最低只能到 Android 11；13 在 cgroup v2 上除了 lmkd 空转（可 stop）之外其它都正常。

## 三、redroid 启动参数（来自官方文档 + 实战贴）

| 参数 | 作用 | 我们用不用 |
|---|---|---|
| `redroid_width/height/dpi` | 逻辑分辨率；**只能启动时定**，`wm size` 会把 redroid 显示搞坏 | 用（720x1280 dpi320） |
| `redroid_fps` | 帧率上限；官方默认 `gpu_mode=guest` 时是 15，硬件 GPU 时 30 | 30（待降到 15 实测） |
| `redroid_gpu_mode` | `guest`=软件渲染（llvmpipe）、`host`=宿主机 GPU | guest（RK3566 无可用 Mali 直通） |
| `redroid_input=touch` | 模拟触摸屏；部分环境不加会让 adb tap 无效 | 用 |
| `use_memfd=1` | 用 memfd 替代 ashmem（Android 12+ 推荐） | **谨慎**：加了这个之后本机 App 起不来（未定论，已回退） |
| `redroid_net_ndns` / `redroid_net_dns` | 指定容器内 DNS；不给就是 8.8.8.8 | 可指定为 192.168.1.1 |
| `use_redroid_overlayfs` | data 拆成 base + diff，多实例共享 | 不用（单实例） |
| `_64only` 镜像后缀 | 纯 64 位 ARM 芯片必须用，否则内核 panic | 未用（当前镜像能跑） |

## 四、UI 自动化怎么做稳

### 1. `uiautomator dump` 在这套环境里是坏的

- 实测：对汽水 App、对系统设置页**都**报
  `ERROR: null root node returned by UiTestAutomationBridge`。→ 无障碍/UiAutomation 不可用。
- 就算能用也不划算：每次 dump 冷启一个 instrumentation，实测 **2~2.4 秒**（弱 CPU 更久），
  而且 `waitForIdle(1000,10000)` 遇到动画（歌词、加载圈、shimmer）会直接超时失败。

### 2. 改用 `dumpsys activity top` 读 View 树（本项目采用）

- 速度：几百毫秒；带 `clickable` 标志和 bounds。
- 注意：**一次 dump 会包含多个窗口**（桌面 QuickstepLauncher + 目标 Activity），
  必须按 `[MainActivity]` 之类的段头过滤，否则会解析到桌面的控件 → 「找到了搜索图标但点了没反应」。
- 汽水的资源 id 基本被混淆（`ho1`/`hky`/`in`），所以只能按**类名 + 位置**定位。实测可用的锚点：
  - 搜索图标：右上角**贴着右边缘**的可点节点（`LunaFrameLayout`，bounds 576,0-720,96）。
    踩过的坑：按「面积最小」挑会挑到图标字体的 `IconFontView`（点上去毫无反应）。
  - 搜索输入框：`LunaSafeAutoCompleteTextView`（类名含 AutoCompleteTextView）。
  - 搜索联想条目：`RecommendPreferenceView`（高约 106）。
  - 搜索结果歌曲行：`TrackView`（高约 144）；**「你可能想搜」卡片是 `ArtistView`，必须排除**，
    点到它只会进艺人主页，白等一个 PICK_WAIT。
- 会话状态必须干净：`am force-stop` + `am start` 之后要**确认真的到前台**
  （`dumpsys activity top | head -2` 里出现 `com.luna.music`），
  固定 `sleep 20` 会 dump 到桌面。**`dumpsys activity activities | grep mResumedActivity`
  在本机不可靠（经常空行），不要用它判前台。**

### 3. 其它可选项（未采用）

- `uiautomator2`（openatx）的常驻 JSONRPC 服务：把 dump 从 2.4s 降到 ~0.2s。
  但它同样依赖 UiAutomation，在本镜像大概率也用不了；且要在设备里塞 u2.jar。
- 截图 + 模板/OCR 匹配：稳但慢，且要处理缩放。

## 五、性能量化（206 / RK3566 / 软件渲染）

| 场景 | CPU | 内存 |
|---|---|---|
| Android 13 / 1200x1848 / 空载 + lmkd 跑 | 192% | 875MB |
| Android 13 / 1200x1848 / 空载 + lmkd 停 | 0.45% | 875MB |
| Android 13 / 1200x1848 / App 前台 | 204% | 900MB |
| Android 13 / 720x1280 / 空载 + lmkd 停 | - | **644MB** |
| 改 720x1280 后 App 前台（粗略，显示已坏） | 40~60% | 760MB |

→ 分辨率对 CPU 的影响是决定性的（软件渲染按像素算），内存只省 ~230MB。

## 六、待验证 / 未定论

1. 720p 容器重启后 **App 拉不到前台**（进程占 300%+ CPU 但界面不出现）。已在同一容器上见过一次成功
   （能走完 首页→搜索→结果→艺人页），说明不是布局问题，疑似与
   「data 从 1200p 容器搬过来」或 `use_memfd` 有关，需要继续定位。
2. `redroid_fps=15` 在 720p 下的实际 CPU 收益（未测）。
3. `redroid_net_dns=192.168.1.1` 是否真的让容器内 DNS 生效（`getprop net.dns1` 取不到值，需要看 ConnectivityService 的 log）。
